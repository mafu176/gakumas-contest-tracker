## Recommendation

Recommended Phase 2 target: **B. stronger fixed ROI/crop separation**, implemented as a runner-only parallel smartphone extractor.

Expected benefit:

- Recovers or preserves 7-digit members before broad row parsing mixes them with totals and bonuses.
- Separates bonus candidates from member slots, reducing bonus-as-member failures.
- Provides the right input shape for future geometry-aware scoring and suspicious-row retries.
- Can be evaluated side-by-side with current output and known corrections without changing production behavior.

Risk:

- Low if kept runner-only and output is advisory.
- Medium if prematurely wired into production, because slot crops may miss values on uncommon device layouts.

Implementation size:

- Medium. Start with JSON-only candidate output using existing fixed smartphone zones and slot-level OCR data where already available.
- Add crop image export either in the same phase or immediately after if slot OCR evidence is hard to inspect.

## Why The Other Targets Are Lower Priority

- Geometry-aware scoring needs cleaner slot/zone candidate sources first. Without stronger ROI separation, bbox scoring still sees mixed total/member/bonus text.
- 7-digit repair candidate generation is tempting but risky. The artifacts show fragments like `19217`, `254.591`, and `$98,088`; repairing these generically without slot provenance would create false positives.
- Suspicious-row retry OCR depends on knowing which crop to retry. Stronger fixed ROI gives the retry system precise stage/side/slot targets.
- Equation solver improvements cannot solve cases where the correct member or bonus is absent from clean candidate lists.
- Debug crop image export is valuable and should be done soon, but it is support tooling. It is best paired with, or immediately after, fixed ROI proposal output.

## Proposed Phase 2 Shape

Add a runner-only smartphone proposal path:

```text
extractSmartphoneRoiCandidates(image, stage, side)
  -> totalBand candidates
  -> memberSlot1 candidates
  -> memberSlot2 candidates
  -> memberSlot3 candidates
  -> bonusBand candidates
  -> wideRow fallback candidates
```

Emit the proposal into debug artifacts:

```json
{
  "proposal": {
    "memberSlots": [
      { "slot": 1, "candidates": [] },
      { "slot": 2, "candidates": [] },
      { "slot": 3, "candidates": [] }
    ],
    "bonusCandidates": [],
    "totalCandidates": [],
    "equationAttempts": [],
    "bestEquation": null,
    "wouldChangeCurrentOutput": false
  }
}
```

Acceptance criteria for Phase 2:

- Current runner output remains unchanged.
- Debug artifacts show proposed slot candidates for all target images.
- At least the known 7-digit failure rows expose whether the missing high member appears in a member slot, wide row, total band, or nowhere.
- No production code path changes and no desktop/PC behavior changes.
